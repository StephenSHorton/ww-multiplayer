# Testing

How changes to this repo are checked: the automated matrix every pull request must pass, the golden files that pin what users see, the tests known to flake, and the checks that need two real Dolphins. Writing tests for a mod is in [api/03-writing-a-mod.md](api/03-writing-a-mod.md#6-testing-with-fakegame).

## The check matrix

Run all of it before pushing. CI (`.github/workflows/build.yml`) runs the same checks: a Linux runner vets and cross-builds the Windows target and runs vet and `go test -race` natively, and a macOS runner vets, tests and packages natively. The maintainers' pre-push script runs the table below in one go on Windows.

| Check | Command | Why |
|---|---|---|
| gofmt | `gofmt -l <changed .go files>` | Format the files you changed only. `internal/inject/dol.go` and `mods/multiplayer/net/backoff_test.go` are not gofmt-clean on main today: never run `gofmt -w` over them (or the module) wholesale, as it would bury your change in a reformat. |
| vet, Windows | `GOOS=windows GOARCH=amd64 go vet ./...` | `wwapi/emu` has a Win32 memory reader. |
| vet, Linux | `GOOS=linux GOARCH=amd64 go vet ./...` | |
| vet, macOS | `GOOS=darwin GOARCH=arm64 CGO_ENABLED=0 go vet ./...` | The cgo memory reader (`wwapi/emu/memory_darwin.go`) is left out of a cgo-off cross-vet; the macOS CI job vets it natively. |
| vet, app window | `GOOS=windows GOARCH=amd64 go vet -tags desktop,production ./...` (and natively on macOS) | The release build compiles the Wails window (`internal/gui`); without the tags `internal/gui` is a stub. CI's `go-vet` action runs both vets on each target. |
| build | `go build ./cmd/ww-multiplayer` and `go build -tags desktop,production ./cmd/ww-multiplayer` | The CLI-only and the release build must both compile. |
| tests | `go test -count=1 ./...` | Everything, including the goldens below. |
| tests, race | `go test -race -count=1 ./...` | Needs cgo (a C compiler); the Linux CI job runs it on every push. |
| fuzz smoke | `go test -run '^$' -fuzz '^FuzzX$' -fuzztime 30s ./pkg` | For each fuzz target in a package you touched, e.g. `./wwapi:FuzzWatcherStep`. List them with `grep -rn "func Fuzz" --include=*_test.go`. |
| manifests | `go run ./tools/validate_manifests` and `go vet ./mods/_fixtures/` | Every `mods/**/mod.json` against the schema (CI's Build workflow). |
| game files | `go run ./tools/check_game_files` | No Nintendo file or save is tracked, or untracked and not ignored (`internal/gamefiles`: names, extensions, file magic, zip entries). CI runs it on every PR, and `release.yml` on the repo and on every release asset. |

C changes (`inject/src`, `inject/include`, `inject/build.py`) also need a rebuilt and restamped blob; `go test ./internal/inject/... ./wwapi/mailbox/...` checks the stamp, the T2 budget and the mailbox layout (CLAUDE.md, "Build pipeline"). `inject/build.py` takes devkitPPC from `DEVKITPPC` (default `C:\devkitpro\devkitPPC`). For a live check of a rebuilt blob, patch a disc with `./ww-multiplayer.exe patch <vanilla> <out.iso>` (the old `inject/patch_iso.py` splicer is gone) and recapture the save states: a state taken on the old blob fails the strict contract check.

Never run the app or the CLI from a test or a check with your real settings: commands like `dolphin2` and the app write config. Point `APPDATA` and `LOCALAPPDATA` (or `XDG_CONFIG_HOME` / `HOME` elsewhere) at a temp directory first. The golden tests below do this for you (`configEnv`).

### Live-disc tests

No Nintendo data is in the repo, so a few tests read the user's own vanilla disc through `internal/vanillatest` and skip cleanly when there is none; `go test ./...` passes either way, and the disc is only ever read. Point `WW_VANILLA_DISC` at the vanilla ISO or CISO; unset, the conventional places are tried (`%USERPROFILE%\Desktop\Dolphin-x64\Roms\` and `~/Roms/`, the file named `Legend of Zelda, The - The Wind Waker (USA, Canada).ciso` or `.iso`). Run them on purpose with `-v` to see they ran rather than skipped:

```
WW_VANILLA_DISC=<path> go test -count=1 -v -run 'Vanilla' ./wwapi/stage ./wwapi/rel ./internal/inject/rels
```

What they pin: every REL in `RELS.arc` re-encodes with `stage.EncodeYaz0` to the exact bytes on the disc (`TestEncodeYaz0VanillaRELs`); `RELS.arc` parsed and saved unchanged by `stage.ArchiveEditor` is byte-identical, and with one REL replaced it parses and reads back (`TestArchiveEditorVanillaRELS`); every REL parsed and saved in place by `wwapi/rel` is byte-identical, repacks to the same module, and `f_pc_profile_lst.rel`'s relocation against the puppet module can be repointed in place (`TestVanillaRELs`); the disc's `RELS.arc` with a dummy REL in module 0x58's place (`rels.PatchRELSArc`) parses, reads the dummy back, has the profile list's entry repointed and every other entry byte-identical, and the ARAM growth guard refuses a guard under the growth (`TestPatchRELSArcVanilla`); the patcher's own path (`rels.PatchISOWithREL`, what `patch` and the app's Setup run) on the whole disc in memory: the output parses, its `RELS.arc` at the new offset parses, module 0x58 reads back as this build's REL with the Layout's prolog, the profile list is repointed, every other entry is the disc's, and patching the output again is `ErrAlreadyPatched` (`TestPatchISOWithRELVanilla`; it holds the decompressed disc and its patched copy, about 3 GB, and skips when `blob.go` has no REL); the disc's `d_a_lod_bg.rel` is the one `rels.SeaHeapFix` was written for (the decomp's SHA-1, expanded or stored), its checks pass, the fix changes that file only with two relocations disabled, and applying it again gives the archive back, and relstest's offline stand-in has the disc REL's section table and the disc's words at the call sites (`TestSeaHeapFixVanilla`; it logs the hashes and where `.text` starts).

## What the goldens pin

A golden file is the expected output, byte for byte. When a golden test fails, the diff is a change a user would see. Fix the code, unless the change is intended; then regenerate the file with the flag below, and say in the pull request which goldens changed and why. A refactor (a file move, a package split) must leave every golden unchanged.

### CLI and help goldens

`cmd/ww-multiplayer/cli_golden_test.go` and `mods_test.go` run `ww-multiplayer <args>` in a child process with its own config directory and Dolphin paths in temp dirs, and compare stdout and the exit code with `cmd/ww-multiplayer/testdata/cli-golden/<name>.txt`:

- `patch-*`: the patcher's lines for a good image, an already-patched one, another version, garbage, a missing file and the usage;
- `help-gui`, `help-nogui`, `unknown-*`: `help` and an unknown command, one file per build (with and without `-tags desktop,production`). They are recorded on Windows, where they compare byte for byte; elsewhere the column padding is ignored but not the text;
- `mods*`: the `mods` command and its flags (`mods`, `mods-json`, `mods-usage`, `mods-dev`, `mods-dev-needed`, `mods-no-multiplayer`, `mods-only`, `mods-unknown-mod`; `TestCLIGoldenMods` in `mods_test.go` drives them). `compiledMods()` lists multiplayer and coop; `mods/example` is in `devMods()` and shows only with `--dev`.

wwdev, the developer tools (`cmd/wwdev`), has its own: `cmd/wwdev/cli_golden_test.go` runs `wwdev <args>` the same way (the harness is `internal/cliutil/clitest`) against `cmd/wwdev/testdata/cli-golden/<name>.txt`:

- `dolphin2-*`: the two-Dolphin bootstrap's messages for each missing piece, `--reset`, and (Windows, no Dolphin running) the launch with `DOLPHIN_EXE` pointed at a directory, so nothing starts;
- `wwdev-none`, `wwdev-help`, `wwdev-unknown`: wwdev's help, with no arguments, `help` and an unknown command (Windows only).

Regenerate on purpose:

```
go test -run 'TestCLIGolden' -update-cli-golden ./cmd/ww-multiplayer
go test -tags desktop,production -run 'TestCLIGoldenHelp' -update-cli-golden ./cmd/ww-multiplayer   # help-gui
go test -run 'TestCLIGolden' -update-cli-golden ./cmd/wwdev                       # dolphin2-*, wwdev-*
```

Run both on Windows, so the help files keep Windows' columns. `cmd/ww-multiplayer/testdata/cli-subcommands.txt` pins the registry's subcommand names (`TestCLISubcommandsUnchanged`); regenerate it with `go test -run TestCLISubcommandsUnchanged -update-subcommands ./cmd/ww-multiplayer` only when a command is added or removed on purpose. wwdev's names are in `cmd/wwdev/testdata/cli-subcommands.txt` (`TestWWDevSubcommandsUnchanged`, `-update-subcommands ./cmd/wwdev`); the two lists share only `help`.

### Co-op golden and converge tests

- `mods/coop/session/golden_test.go` (`TestGolden*`) drives the co-op questions, offers and console flows and compares every logged line, with its level, with `mods/coop/session/testdata/coop-golden/*.txt`: the prompter, the offers (stdin and controller), and the console (stdin, host, two players, dry run, writing). Regenerate on purpose with `go test -run TestGolden -update-coop-golden ./mods/coop/session`
- `mods/coop/session/converge_test.go` (`TestCoopSessionConverges`, `TestCoopFreshBindRestart`) runs two fake games through a loopback session with out-of-order, repeated and dropped messages and a host restart, and checks invariants: the world is the merge of both games' shared progress, the replicas converge, clears never propagate, the only writes are the binding tags, and no per-player byte crosses the wire. There is no file to regenerate. A change to what they assert is a change to co-op's behaviour and needs the owner's M2-M6 rerun below.

A change that moves co-op code (the `mods/coop` packages, `wwapi/write`, `wwapi/state`, `wwapi/gate`) must leave both byte-identical: same golden files, same assertions.

## Known flakes

These tests are known to fail now and then on timing, without a code change behind it. Rerun the job once. If it fails again, treat it as a real failure.

| Test | Where | Why |
|---|---|---|
| `TestControllerQuestions` (`mods/coop/session/controller_test.go`) | macOS CI | The co-op controller's question flow under a slow runner. |
| `TestLobbyKickClosesLobbyAndPlayerConns`, `TestLobbyKickSticks` (`mods/multiplayer/net`) | any | Loopback connections closing around the kick. |
| `TestUpdateInstall` (`internal/gui`) | any | Failed once with "new version didn't start (file not found)" on a branch that did not touch `internal/gui`, then passed three reruns. Cause not found. |
| `TestCoopSessionM4` (`mods/coop/session`) | macOS CI | Failed once on the `/status` max hearts line, then passed on the rerun. Cause not found. |

Any other failure that passes on a rerun is a new flake: report it, do not just rerun it away.

## Live checks on two Dolphins

Unit tests cannot see a rendered frame. Changes to the pose pipeline, the puppets, the mailbox or the C side also need the owner's machine with the two-Dolphin harness (CLAUDE.md, "Standard session bootstrap"):

```
SAVE_STATE=$(pwd)/saves/start.sav ./wwdev.exe dolphin2
./wwdev.exe mp-local
```

Accept anything visual only on a screenshot pair (`WW_DOLPHIN_INDEX=0` and `=1`, `./wwdev.exe screenshot`), never on a memory readback.

### The smoke checklist (design decision 11)

After a change to the multiplayer pipeline (`mods/multiplayer/feed`, `wwapi/avatar`, `wwapi/player`, the tunic feed, the mailbox):

1. **Pose**: each Dolphin shows the other's Link where he stands, animating (walk, roll, swing), with no T-pose or frozen frame.
2. **Face**: the remote Link's eyes and mouth move (blinks, the look direction).
3. **Colors**: each remote Link wears his player's tunic color (`--color`), and stays in it after the steps below.
4. **Stage change**: one player goes through a loading zone. His Link leaves the other's screen, and both show again once they are back in the same stage.
5. **Leave and reset**: one player stops (Ctrl+C, or leaves the lobby). His Link disappears from the other's game within the despawn time, and `mp-local` on Ctrl+C resets `shadow_mode` on both Dolphins. A new session afterwards works without restarting Dolphin.

A third player (a `fake-client` or `pose-fake-loop` next to `mp-local`) is not on the list. It used to freeze both Dolphins (F1 in [05-known-issues.md](05-known-issues.md)); that was fixed and cleared live for both variants on cea51fe, and three remotes are now mini-Links (WWMB layout 3). Its check is "Three remotes and the soft reset" below (R3-1).

### Co-op M2-M6 rerun

After a change to co-op behaviour, or a move of its code that the goldens cannot fully cover (C13's `wwapi/write` split is still waiting for it), the owner reruns the co-op acceptance steps on two Dolphins with `mp-local --coop`, in the order of [08-coop-design.md §8.2](08-coop-design.md#82-owner-machine-two-dolphin-harness):

- **M2** (dry run, `--coop-dry-run`): binding and the planner's log;
- **M3** A1-A6 and the escapes R1-R4: chests, pickups, rooms, dungeon items, switches, ocean and charts;
- **M4** P1-P9: story bits, items, songs, capacities, keys, hearts and magic;
- **M5** Z1-Z6: live room puzzles;
- **M6.0** K1-K10: the kill union and the light-shrink.

Each section of §8.2 lists its fixtures (F1-F5 save states) and steps.

### Co-op: the stale-actor refresh, Tiers 1 and 2

Design: `ww-multiplayer-handoff/design/stale-actor-refresh.md` (Tiers 1 and 2, G1-G4, with its Check notes). An actor that reads its bit only in create stays stale when the partner's bit lands after it was created. The replica now keeps a **landed set** (`mods/coop/replica/landed.go`): the bits its own writes set and the next Observe verified, per bit (new &^ old), from the merge path (live memBit chests, memory switches, pickups 0-31), the scoped path (dan, zone and room switches) and the kill path. It is cleared on a stage, table or file change and on a save state. The refresh (`refresh.go`) acts only on an actor whose bit is in that set, never on a bit that just reads set, so the receiver's own play is never touched. It runs inside the M6 tick and needs FeatureCombat, not a dry run.

- **Tier 1, the key-door lock** (`writer_lock.go`): a DOOR10 or DOOR12 whose lock switch (a small-key door, or a boss door with swbit < 0x80) landed gets one byte, `dDoor_key2_c.mbEnabled` 1 to 0 (DOOR10 +0x308, DOOR12 +0x2E4). This is held while the unlock animation plays (m20, lock +0x20), while an event has ordered the door, while neither of its rooms is loaded and settled, while Link is in a demo or within 300 units (x-z) of the door, and for the settle time (1 s). Each door is cleared at most once. Log: `co-op: refresh: cleared the stale lock of actor 0x... (pid n, proc 0x012E , ...): its switch 0x36 landed`.
- **Tier 2, the death switch**: a K1 enemy whose death switch (home.angle.z's low byte) landed is light-shrunk by a second allow rule of M6, with all of M6's gates. #!/usr/bin/env bash
```bash
# hkforce.sh <pid> <mode>: down | mask | zero | req | flag | sword
export WW_DOLPHIN_PID=$1
P(){ ./wwdev.exe poke-u32 $1 $2 >/dev/null 2>&1; }
word(){ ./wwdev.exe peek $1 4 | awk '{print $2}' | head -1; }       # 0x-prefixed
RMWA(){ w=$(( $(word $1) )); P $1 $(printf %08X $(( (w & $2) | $3 ))); }
A(){ printf %X $((bdk+$1)); }                                         # a Bdk field's address
RMW(){ RMWA $(A $1) $2 $3; }
# phase 1 -> T_DOWN, as the hammer hit's m2B4==1 branch (.text 0x4AE8-0x4AF4): mState first, mAction last
down(){ RMW 0x2C8 0x0000FFFF 0x00000000; RMW 0x2C4 0xFFFF0000 0x00000067; }
# the fourth mask hit, as .text 0x4BB4-0x4BC0: m8F8 3, mAction 9, then mState 0 last. Poke it while the bird is in
# KUTI_ATTACK with the beak stuck in the floor (bdk-probe's mAction 0x5 with mState 5 or 6; earlier kuti states undo
# it), as a real hammer hit on the head would be: the demo's camera step puts Link
# beside the bird every frame (demo_camera case 2, d_a_bdk.cpp setPlayerPosAndAngle, y kept), so a mask broken with
# the bird hovering near the west wall (x below about 2400) puts Link past the edge and he falls through to a void-out
# (seen with no multiplayer process running). Not the game's order: a frame between
# the two pokes runs the bird's current fight action, which moves mState 0 -> 1, and kamen_demo entered at step 1 skips
# step 0's m25A0 1 and waits at step 2 forever (seen live). mState last restarts kamen_demo at step 0 whatever ran between.
mask(){ RMW 0x8F8 0x00FFFFFF 0x03000000; RMW 0x2C4 0xFFFF0000 0x00000009; RMW 0x2C8 0x0000FFFF 0x00000000; }
# P0 only: the pending zero by hand, keeping max_health and the pad
zero(){ RMW 0x284 0xFF00FFFF 0x00000000; }
req(){ ack=$(word 80413418); P 80413414 00F0424B; P 80413410 $(printf %08X $((ack+1))); sleep 0.8; ./wwdev.exe peek 80413410 16; }
flag(){ RMWA 803C5258 0xFFFFFFFF 0x00010000; ./wwdev.exe peek 803C5258 4; }
sword(){ P 803C4C14 FFFF393B; RMWA 803C4CBC 0x00FFFFFF 0x03000000; }  # then stage-hop
case $2 in
down|mask|zero) bdk=$(./wwdev.exe bdk-probe 2>&1 | awk '/^  bdk at/ {print $3; exit}')
  [ -n "$bdk" ] || { echo "no Bdk (bdk-probe)"; exit 1; }; $2 ;;
req|flag|sword) $2 ;;
*) echo "usage: hkforce.sh <pid> down|mask|zero|req|flag|sword"; exit 2 ;;
esac
```

### Patcher: the optional sea heap fix (`patch --fix-sea-heap`)

### Dev tooling: Dolphin logs, run logs, crash-context

`WW_DOLPHIN_DEVLOG=1` makes `wwdev dolphin2`, `auto-recapture` and `auto-recapture-pair` launch Dolphin with `launch.DevLogArgs`: session-only `-C` keys that write `<user dir>/Logs/dolphin.log` (Info; OSReport EXI and HLE, MI, MASTER) and turn the panic popups and the stop confirmation off. No ini file of any profile is written. Because Dolphin appends to `dolphin.log` and nothing truncates it, a dev-log launch runs only on user dirs set explicitly with `USER_DIR_1` / `USER_DIR_2` that are no player's profile: it refuses, before launching or killing anything, when the variable is unset or names `%APPDATA%\Dolphin Emulator` (the default), `Documents\Dolphin Emulator` (also under OneDrive), the registry's `UserConfigPath`, the portable `<Dolphin.exe dir>\User`, or on Linux/macOS the matching defaults (`launch.DevLogUserDirError`). The `[Logs]` keys are Dolphin's short channel names (`MI`, `MASTER`), read from Dolphin 2609a's binary, not the `MEMMAP` / `MASTER_LOG` enum names. `wwdev mp-local` writes `logs/latest/` (`WW_DEV_LOGS=<dir>|off`): `mp-local.log` (its own output), `session.json` (start and end, the outcome (`ok`, `interrupted`, `force quit`, `error: ...`; stamped on every exit, an early error exit and a second Ctrl+C included), the binary's VCS revision and dirty flag, blob.go's blob and REL hashes, per Dolphin the PID, user dir, save state and its SHA-256, and the contract verdict: blob CRC and REL build id) and `dolphin-A.log` / `dolphin-B.log` (each Dolphin's log from its launch, by `logs/dolphins.json`, which `dolphin2` writes); the run before moves to `logs/sessions/<its start>/`. `MP_LOCAL_DOLPHIN_LOG=1` also prints the Dolphin lines in mp-local's output as `[dolphin-A]` / `[dolphin-B]`. A `dolphins.json` record names a PID only while that process has the record's start time, so a later Dolphin that got the PID again is treated as unrecorded. `wwdev crash-context` reads the crash JUTException caught (`wwapi/crash`).

### Dev tooling: the scripted smoke and the smoothing step log (ww-online review 23)

`wwdev smoke` runs the two-Dolphin smoke unattended and exits 0 (every check passed), 1 (a check failed) or 2 (it could not run: no Dolphins, a refused user dir, mp-local never armed, Ctrl+C). datstarkey/ww-online's native test passes once frames were reached and screenshots saved (`scripts/dev-test-native.sh:155`); this one checks sync at memory level.

- **Setup.** With no Dolphin running it boots two with `dolphin2` and `WW_DOLPHIN_DEVLOG=1`, which needs `SAVE_STATE` and `USER_DIR_1` / `USER_DIR_2` set to test dirs that are no player's profile (`launch.DevLogUserDirError`). Neither mode drives a Dolphin on a player profile or on dolphin2's own second default (`%APPDATA%\Dolphin Emulator 2`, the bootstrapped second profile with real cards). With two running it attaches only to a Dolphin `logs/dolphins.json` records as a `WW_DOLPHIN_DEVLOG` launch of that very process (its start token matches; that launch already refused anything but an explicit test dir), or, for any other Dolphin, when `USER_DIR_1` (A) or `USER_DIR_2` (B) is set explicitly to its test dir (and agrees with its record when it has one; a declared dir is not checked against the process otherwise). A and B are `MP_LOCAL_PIDS` when set, else `dolphins.json`'s live "Dolphin 1" and "Dolphin 2" (also with more than two running), else the two running in order. One running Dolphin, or more than two with neither, is refused. Both games must be in-game, pass the contract check and have a moving heartbeat before `mp-local` starts as a child (`mp-local up` then wants a `pose_seqs` byte changed since those samples, so a feed left armed by a killed run does not pass it): `MP_LOCAL_PIDS` pins A and B, and `MP_LOCAL_STOP_FILE` ends it with its own teardown at the end (after 30 s it is killed and smoke clears both pose feeds itself).
- **Per game.** The heartbeat (`spawn_trigger`, at least 10 frames/s and moving at every 100 ms sample); the REL linked with this build's id and its frame counter moving; nothing caught by JUTException; the visuals block's last-error word 0 or unchanged from before mp-local started (the REL never clears it, so one left by an earlier session is reported as a `(pre)` note, and only a new value fails); `pose_publish_seq` and a `pose_seqs` byte changing (counted as changes: NextSeq skips 0) with `shadow_mode` 5.
- **Walk.** Each Link in turn walks `--walk-ms` (default 1500; four stick directions are tried until it moves `--min-move`, default 100). After a settle the other game's puppet slot and mini-Link root for it must be within `--tol` (default 50) of its Link and its published root.
- **Hop.** A hops to `--hop` (default `sea 0 44`, checked against `ISO_PATH`'s disc as `stage-hop` does; `none` skips; a target that is the stage A is in fails, so from Outset (`sea` room 44) give another stage) and back to its start; both heartbeats keep moving and the walk check passes again.
- **Optional.** With `-- --coop=...` both files must be bound to one world (`bind.Classify`); with `--switch N` memory switch N set on A must show on B within 20 s; with `--smooth <rate>` the smoothing below runs as one more check (pass/fail only with `--smooth-max-cv`).
- **Report.** `logs/latest/smoke.json` (every check with its numbers, the failed list, the outcome, the log paths) and `smoke.log`, beside mp-local's `mp-local.log`, `session.json` and `dolphin-A/B.log`. `--out` writes a copy; `-v` echoes mp-local's lines.

`wwdev smooth-steps [secs=5] [A|B]` measures smoothing as a number, after ww-online's `COS_MP_TEST_STEPS` (`seaborne/native/src/mods/ww_online/README.md:112-181`). With mp-local running, the walker's Link walks straight while both games are sampled every frame (each game's `spawn_trigger` is its clock): the walker's Link, and the other game's puppet slot for it (the root the mini-Link's pose is re-applied at). Over the stretch at speed it reports each trace's per-frame step (mean, sd, cv, min, max, median), stalls (a frame under a tenth of the walker's median), jumps (over twice it), jerk (the RMS step-to-step change), the remote's mean step over the walker's (ratio) and how far behind it trails. The run, both traces included, goes to `logs/latest/smooth-steps.json`, with the running mp-local's `WW_POSE_TEST_RATE` read from its `logs/latest/session.json` (`rate`, and `rate_from` saying where; `unknown` with logs off or no running session). Like smoke it drives only test Dolphins (the attach rule above), and Ctrl+C mid-walk releases the stick before it exits. A frame gap over 30 (a save state loaded) is left out as a discontinuity. `WW_POSE_TEST_RATE=<hz>[:<jitter ms>[:<latency ms>]]` on wwdev's broadcasts (`feed.TestRate`; the shipped binary has no such knob) samples at that rate and sends each sample late by the latency plus up to the jitter, in order, as their `COS_MP_TEST_RATE` does (their proof run: `20:40:20`).
