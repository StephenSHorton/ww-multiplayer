# Architecture

## Goal

Enable two players to see each other in Wind Waker on Dolphin — each player runs their own Dolphin instance with their own save, and sees the other player's Link walking around in real-time.

## Three-Layer Design

```
┌──────────────────────────────────────────────────────────┐
│                    Player A's Machine                    │
│                                                          │
│  ┌─────────────┐     ┌──────────────┐     ┌──────────┐  │
│  │   Dolphin   │◄───►│  ww-mult Go  │◄───►│  Server  │  │
│  │ + WW (GZLE01)│    │              │     │(TCP:25565)│  │
│  └─────────────┘     └──────────────┘     └────┬─────┘  │
│         ▲                    │                 │        │
│         │                    │                 │        │
│         └─ ReadProcessMemory │                 │        │
│         └─ WriteProcessMemory│                 │        │
│                                                │        │
│                                                │        │
└────────────────────────────────────────────────┼────────┘
                                                 │
                                          TCP over LAN
                                                 │
┌────────────────────────────────────────────────┼────────┐
│                    Player B's Machine          │        │
│                                                 │        │
│  ┌─────────────┐     ┌──────────────┐         │        │
│  │   Dolphin   │◄───►│  ww-mult Go  │◄────────┘        │
│  │ + WW (GZLE01)│    │ (client mode)│                  │
│  └─────────────┘     └──────────────┘                  │
└──────────────────────────────────────────────────────────┘
```

## Data Flow

1. Each Go client reads its local player's position from Dolphin memory at ~60fps (50ms intervals).
2. Position data is sent to the server via TCP.
3. Server broadcasts position to all other clients.
4. Each client writes the received position to a "second Link" actor in its Dolphin memory.
5. The game renders the second actor at the received position, creating the illusion of another player.

## Components

### `wwapi/emu/`

Windows process memory access via `kernel32.dll` P/Invoke (ReadProcessMemory / WriteProcessMemory). Handles:
- Process discovery (find Dolphin.exe)
- Memory base scanning (locate emulated GameCube RAM in Dolphin's process — works on any Dolphin version including modern 64-bit builds)
- Big-endian / little-endian conversion (GameCube is big-endian, x86 is little-endian)
- Read/write at absolute GC addresses (`Read`/`Write`, bounds-checked to MEM1; a `*emu.Dolphin` is a `mem.Mem`). `emu.Attach(Options)` picks the process; package main fills the options from `WW_DOLPHIN_PID`/`WW_DOLPHIN_INDEX`. Window, screenshot and key input are in `wwapi/emu/host`.

### `mods/multiplayer/net/` (package `network`)

Simple TCP-based protocol with message framing (`[type:1][length:2][data]`). Message types:
- `J` (Join) — client announces name
- `H` (Hello) — protocol version, and from protocol 2 the connection role and caps (`handshake.go`)
- `W` (Welcome) — server assigns an ID; `R` (Reject) — the server refuses the connection, with a code and a reason
- `P` (Position) — 18-byte position update (3 floats + 3 int16s); `M` (Pose) — the skeletal pose
- `L` (PlayerList) — server announces who's connected (with the tunic-color trailer, docs/09); `D` (Leave)
- `C` (Chat) — text messages
- `K` / `Q` (Ping / Pong) — heartbeat and RTT
- `O` (Coop) — co-op sub-messages, on a co-op connection only (docs/08)
- `B` (Lobby) — lobby sub-messages with JSON bodies, on a lobby connection only (docs/10-lobby.md)

A connection has one of three roles, set in its hello: a **player** (pose, position, chat and the roster; every CLI connection), a **co-op** connection (`RoleCoop`, the co-op pipeline), or a **lobby** connection (`RoleLobby`, the desktop app's pre-game lobby: members, colors, ready flags, the host's co-op settings, Start). Co-op and lobby connections are never players: not in the roster, the player count or the relays. Every server has a lobby (`LobbyHub`), inert until a lobby connection arrives; a server from before the lobby refuses the role with `RejectRole`, and the app then joins directly, so the protocol version stayed 2. The server's `CoopHandler` can be set after `Start` (`Server.SetCoop`); while the lobby's host has chosen co-op and the session isn't in game yet, a co-op hello is held for it instead of refused, and `Stop` releases a held one (docs/10-lobby.md §7). A name the lobby's host kicked gets `MsgReject` (`RejectBadName`) on player and co-op connections until the lobby empties, so a reconnecting CLI join stops. Lobby connections are rate-limited and STATE is merged per connection, so a member can't make the server flood the others (docs/10-lobby.md §3).

Server runs on port `25565`. UDP would be lower-latency for position data but TCP is fine for LAN play.

### Front ends and `internal/session`

One exe has three faces (`app_face.go`). Every subcommand is the CLI, dispatched by the command registry in `commands.go` (which replaced main's switch in Phase B1) exactly as before; running with no arguments opens the desktop app window (`internal/gui`, below), or, in a build without the window, the Bubble Tea TUI (`internal/tui`, brought back in v0.1.5 after v0.1.2 removed the v0.0 one), which `ww-multiplayer tui` always opens; `ui` opens the window too and `ui --browser` serves its UI to a browser. `TestCLISubcommandsUnchanged` pins the registry's subcommand list to the one before the window (`testdata/cli-subcommands.txt`) and checks none of them opens anything but the CLI. The CLI faces:

- `ww-multiplayer.exe host` / `ww-multiplayer.exe join <ip>` — the user-facing multiplayer entry points (one process per player; signal handler resets the mailbox on Ctrl+C).
- `ww-multiplayer.exe server` / `broadcast-pose` / `puppet-sync` — lower-level building blocks. `mp-local` runs the same pipelines in one process for the two-Dolphin local harness; the legacy `scripts/mplay2.sh` runs them as separate processes.
- `ww-multiplayer.exe debug`, `ww-multiplayer.exe dump`, `ww-multiplayer.exe shadow-mode` — diagnostic CLIs. Plain-text output — good for piping into agents.

The front ends do not call the session code directly. They drive a **session controller** (`internal/session`), the UI-free owner of a session's state that the desktop app (`internal/gui`) drives too:

```
CLI host / join        TUI (internal/tui)        GUI (internal/gui + frontend)
        │ commands: Host, Join, Leave, SendChat; co-op: Answer, Command, CommandLine
        │ lobby: HostLobby, JoinLobby, SetColor, SetReady, SetCoopSettings, Start, Go, Kick, RequestMerge
        │ out: Snapshot() State, Subscribe() <-chan Event, Wait(id) State
session.Controller (internal/session)
        │ Engine (+ CoopEngine) interface, injected by main
engine.Engine (mods/multiplayer/engine) ── RunHostSession / RunJoinSession (+ LiveState for the TUI and GUI; co-op through engine.CoopApp = coopsession.App, mods/coop/session/hook.go)
```

- **Commands in.** `Host(ctx, HostOptions)` and `Join(ctx, JoinOptions)` start a session in the background and return its `ID` (one session at a time; `ErrBusy` otherwise). The options carry the port (host) and the co-op choices (`CoopOptions`, the `--coop` flags). `Leave` cancels it and returns once teardown is done (pipelines stopped, server unbound, mailbox reset), so the next Host can bind the port. `SendChat` forwards a line to the running session. `Wait(id)` blocks until a session has ended and returns its final state.
- **State out.** `Snapshot()` returns a copy of the current session's `State`: ID, phase (`Idle → InGame → Ended`), role, name, address, end reason, `Failed` (it ended on an error), its co-op options, its open co-op questions, and the live values (players, player count, host addresses, latency, own position, each co-op pipeline's `CoopStatus`) the engine reads from `engine.LiveState` and the co-op console. The dashboard polls it every 250 ms.
- **Events out.** `Subscribe()` gives each UI its own buffered channel of `Event`s: `EventLog` (every `log.Reporter` line), `EventChat`, `EventEnded` (with the end reason: the newest Err-level line, or "no error was reported"), `EventState`, and for co-op `EventQuestion`, `EventQuestionClosed` and `EventAdvice`. Every event carries the session `ID`, so a UI ignores late events from a session it has left. A full buffer drops its *oldest* event, so a slow UI never stalls broadcast-pose or puppet-sync and a session's last two events (`EventEnded`, then `EventState`) always get in (`New` keeps every buffer at 2 slots or more for that).
- **Engine.** `internal/session` imports neither `wwapi/emu` nor `mods/multiplayer/net`; package main injects the work as a `session.Engine`. `engine.Engine` (mods/multiplayer/engine, built by package main's `newTUIEngine`/`newCLIEngine`) runs `engine.RunHostSession` / `engine.RunJoinSession` (co-op goes in through the seam in `engine/coop.go`: `engine.CoopApp`, `coopsession.App` (the app's) or `coopsession.CLIApp` (mods/coop/session, over the `coopsession.Env` package main hands it), gives a host or join session its `engine.Coop`, `coopHook` in `hook.go`, and a lobby session its `engine.LobbyCoop`, `appCoop` in `app.go`), hands them a per-session `session.Output` (a `log.Reporter`, from `wwapi/log`, a chat sink, `Ask` and `Advise`) and reads `engine.LiveState` for `Live()`. An engine that also implements `session.CoopEngine` (`Command`, `CommandLine`, `CoopWorlds`) takes the co-op console verbs; the controller finds it by a type assertion, so an engine without co-op needn't. An engine error that the session already logged (a fatal connect error) wraps `ErrReported`: the controller doesn't log it again but still marks the session `Failed`. The controller is unit-tested on any OS with a fake engine.
- **The lobby.** `HostLobby` and `JoinLobby` start a session that begins in the pre-game lobby (docs/10-lobby.md). Its phase follows the host's lobby, `Connecting → InLobby → Starting → InGame` (the new phases are numbered after `Ended`, so the old values keep theirs), and `State.Lobby` holds the lobby's view: this player's member ID and host flag, the phase, the co-op settings and every member (name, color, ready, Dolphin state, file hint, RTT, `app` or `cli`, away), plus the lobby connection's health (`Lobby.Link`: connecting with its failed attempts, up, or reconnecting since a drop; the engine reports it through `LobbyOutput.LobbyLink` from the lobby client's `OnLink`). The lobby commands (`SetColor`, `SetReady`, `SetDolphin`, `SetFile`, and for the host `SetCoopSettings`, `Start`, `Go`, `Kick`; `RequestMerge`) go to an engine that also implements `session.LobbyEngine`, found by a type assertion like `CoopEngine`; the controller refuses what the role or phase rules out (`ErrNotHost`, `ErrWrongPhase`, `ErrColorsLocked`, `ErrNoLobby`) before anything is sent. The host's replies arrive as `EventLobbyNotice`, `EventLobbyStart`, `EventLobbyGo` and `EventLobbyRequest`. A host whose build has no lobby makes `JoinLobby` fall back to the direct `Join` in the same session (`EventLegacyHost`, `State.Lobby.Legacy`), which the GUI does automatically (owner decision), keeping the chosen color (`JoinOptions.Color` reaches the direct join's player connections). A member that joins or reconnects after Start still gets `EventLobbyStart` (and, in game, `EventLobbyGo` with the world); handlers treat a repeat as idempotent. `engine.Engine`'s lobby side is `mods/multiplayer/engine/lobby.go`; what Start launches is below, and no CLI subcommand opens a lobby.
- **Start → Dolphin → in game (App PR 8, design §2.6).** `Start` is the host's and waits for every other member to be ready (`Lobby.NotReady`, an away member counts as not ready; the host's own flag isn't asked for): it returns `ErrNotReady`, and `StartAnyway` skips the wait. On START (and on its replay to a late joiner or a reclaim) each app's engine starts its game side, `engine.GameRunner` in `mods/multiplayer/engine/game.go`, once per session. It reads the player's launch options at that moment (`HostOptions/JoinOptions.LaunchFn`: the GUI's saved Dolphin, user folder, patched disc, "I'll start Dolphin myself" and cheats) and decides with `session.DecideLaunch`: attach to a running Dolphin on this player's user folder (`launch.Processes` reads each Dolphin's command line on Windows: its `-u`, else the folder its program uses), so two players on one computer never take each other's Dolphin; a player who starts Dolphin themselves also attaches to a Dolphin running Wind Waker on another folder (one opened without `-u` runs on its program's default folder), but never to one started with an explicit, different `-u` (`RunningDolphin.Explicit`: another player's, usually another app's launch) or one whose mailbox `shadow_mode` is already set (`Claimed`: another session plays on it), and otherwise waits for one; Start (`Bridge.Start`) refuses for want of a Dolphin or patched disc in Setup only when this decision would launch; otherwise launch the configured Dolphin with the patched disc (`launch.Launch`, the bundled cheats first unless a `GZLE01.ini` is there). `WW_DOLPHIN_PID` names the Dolphin outright. The runner then looks at the Dolphin once a second (`session.DolphinStateOf` of a probe: the process, `emu.DiscID` (the game ID beside the GC disc magic at the start of emulated RAM), this build's injected code at `inject.T2Address` (90% of `inject.T2Bytes`' non-zero bytes), `player.Link.Ready`): `launching`, `title`, `in_game`, `no_game`, `wrong_game`, `unpatched` or `none`; a wrong game or unpatched disc must be seen twice before it is reported (a boot can be caught mid-way), and until then a Dolphin just attached to counts as `no_game`, never as closed (only a probe that finds no process is `none`). The state goes to the controller (`LobbyOutput.Dolphin`, `State.Dolphin`) and to the lobby (`SetDolphin`, every member's Dolphin chip). As soon as the Dolphin runs the patched game, title screen included, the pose pipelines (broadcast-pose + puppet-sync, `runPosePipelinesOn`) run on that PID, so remote Links show on the title screen (#38); the pipelines register their client and position with `engine.LiveState` for the Session screen, not their chat (a lobby session's chat comes on its lobby connection). A Dolphin that closes stops the pipelines (state `none`, the "Dolphin closed" banner, `LaunchDolphin` launches it again); so does one that stops running the patched game for two looks in a row (emulation stopped, or another boot in the same Dolphin): their handle and RAM base are the old boot's, and they start again on the new boot; a fatal pipelines error (a version mismatch) ends the session; any other restarts them. The host answers its own START with GO at once while co-op is off (`goIfHost`), and the lobby goes in game; with co-op on, GO waits for the world (below). Leave (or a session that ends) stops the runner before the lobby connection and the host's server: the pipelines stop (puppet-sync turns the tunic slots off), then each Dolphin they ran on gets its mailbox reset (`resetMailboxOn`: shadow_mode 0, pose seqs 0, tunic enables 0 unless `WW_TUNIC=off`), only while it still runs this build's mod (`hasThisMod`: a Dolphin that booted the vanilla disc since has game heap there); the Dolphin keeps running. A member's Dolphin state also travels in its HELLO, and a reclaim takes it, so a `LOBBY_SET` lost while the link was down doesn't leave a stale chip. Tests: `internal/session/launch_test.go` (the decision, the state mapping, Start's rules) and `mods/multiplayer/engine/game_test.go` (the runner with fake Dolphins from `engine/enginetest`, and two apps plus a late joiner through a real lobby on loopback: launch, GO, in game, the teardown order).

- **Co-op in the app (App PR 9, design §2.5-§2.8, §3.6; `mods/coop/session/app.go`, `internal/session/coopapp.go`, `internal/gui/coop.go`, `cards.go`, `frontend/coop.js`).** The host's lobby settings choose co-op: Off (the default, and a choice like the others: owner decision), New world, or Continue a world on this computer (`CoopWorlds`), with Advanced: dry run, allow merging, live switches, and the disc the co-op tables come from (`--coop-iso`; by default the patched disc Dolphin boots). `Bridge.SetCoop` sends them (`SetCoopSettings`, with the world list as a summary) and saves them as the config's `coop` section. The work is the CLI's `--coop` session, started at another moment and on this player's own Dolphin and user folder, so the log lines are the CLI's (`TestAppCoopHostLogsMatchCLI`):
  - **Host, on START** (`appCoop.OnStart`, its `engine.LobbyCoop` hook): `startCoopSide` (the backup of the cards of the player's Dolphin user folder, the stage tables), then `Session.openWorld`, the CLI's world step: Continue opens the world; New world founds it with `appCoop.found` instead of `foundCoopWorld`, on the Dolphin the game side plays on (`engine.GameRunner.PlayablePID`), reporting each look to the window (`session.Founding`, the guided dialog's live check), logging the CLI's waiting line every 5 s, and for a file that can't found a world (bound already, a newer tag, a second quest: `foundCheck`, the CLI's own refusals) it says why once and waits for another file or for "Remove the tag" (`UnbindFile`: `coop-tag clear --yes` for the app, in game memory only). Then `startHub`, `Server.SetCoop(hub)` and only then GO with the world's ID; a world that can't be opened or founded is logged, and GO goes out without a world (no co-op).
  - **Joiner, on GO** (`appCoop.OnGo`): only a GO that names a world starts its co-op side (`startCoopSession`, with its own dry run if ticked, `HostOptions/JoinOptions.CoopFn`), so its co-op connection never meets a server without a hub.
  - **coop-sync** runs beside the pose pipelines on the same Dolphin (`engine.GameRunner.SetCoop`, `engine.GameDeps.CoopSync`), from the next look once co-op started; it stops with them (Dolphin closed, Leave) and restarts after an error, a Dolphin relaunch or a new boot (`appCoopSync`; each run leaves the console when it stops, the console keeps the session's context, and a no to a bind question holds across runs). Warps find the partner through the status bridge's puppet-sync client (`Session.poseClient`). The hub stops after the server, which removes the world's session marker.
  - **Merging after Start**: the host's "Allow merging" sets the lobby's settings' merge (the one setting the lobby lets change in game); the host's engine turns it on in the hub (`hub.SetMerge`, which tells every peer its features again), and a joiner whose unbound file needed it asks to bind again once its replica has the merge feature (`Session.retryBinds`).
  - **Controller**: `State.Founding`, `State.CoopBackup`, `State.Advice` (kept until dismissed, the newest per kind and player: `DismissAdvice`), `State.Requests` (a joiner's merge request on the host: `AllowMerge`, `DismissRequest`), `State.AutoYes` (`SetAutoYes`: "Answer yes to co-op questions", per session, never saved), `UnbindFile` (a `CoopFileEngine`), and the engine's `CoopOutput` (`Founding`, `Coop`: the options the session runs with, `Backup`). `Question` names the file, the worlds and a scrub's failed checks; `CoopStatus` carries the pipeline's state structured (state code, writes off and why, the file's tag state, the last preflight, progression, puzzle, combat and Tingle Tuner lines, the partner's place), and `Live.CoopHub` the host's hub (world, seq, features, merge, peers).
  - **Window**: every player's card-file preview (`cards.go`: `backup.Locate` on the player's user folder, `savefile.Read`, the three files with name, heart containers and bind state for the chosen world, a hint, and its short ASCII form sent as the member's lobby file hint, shown as a chip on every row); every co-op question, advice and request as a dialog decided in Go (`coopDialog`: the founding while it waits, then the oldest question, a merge request, advice, a file bound to another world, then "World … founded"); Escape on a question is its no, as on the command line, and a close the window makes itself is not. A question or a "Remove the tag" dialog takes the focus itself and ignores input for its first 600 ms (`SETTLE_MS`, Appendix C items 64, 164 and 165). "Remove the tag" (`UnbindFile`) carries the tag's world the dialog showed, and refuses for another file's tag or the session's own world. The Session screen's co-op panel (`coopPanel`, from `CoopStatus` and `CoopHub`, not `/status` text) with Refresh area, Warp to partner, Pause/Resume co-op writes (the console's verbs through `Command`) and Copy status (`CoopStatusText`, `/status`'s text); a `/` line typed in the chat box goes to the console. The banners "Founding the new world: …" (with Remove the tag while a bound file blocks it), "Co-op writes turned off: …" (with Resume) and "File not bound." (with Remove the tag for a file bound to another world). The log panel's tabs: Chat, Co-op sync (the co-op lines users care about, `syncLine`) and All logs.
- **Join codes and LAN discovery (App PR 11, design §2.2-§2.3 and decision 12; `internal/netutil/joincode.go`, `internal/lan`, `internal/gui/lan.go`).** No service is involved. A **join code** is the host's IPv4 and port in Crockford base32 with a check symbol (`WW-XXXX-XXXX` on the default port, `WW-XXXX-XXXX-XXXX` otherwise; docs/10-lobby.md §10). `netutil.NormalizeAddr` and `ValidateAddr` take one, so the app's Join box, the TUI and the CLI's `join` all accept a code (any case, dashes optional, I/L read as 1 and O as 0, a typo caught by the check symbol and refused, never dialed as a host name); the CLI's output is unchanged. The host's share card shows a code under each IPv4 address. A code holds the address, so it is masked exactly like one (owner decision "hide IP addresses by default"): `redact.Addr` and `redact.Text` mask any code-shaped token to `WW-••••-••••`, the card's Show reveals the address and its code together, Copy code copies the real one, and the header switch shows them all; Copy diagnostics and the log panel mask them as text. **LAN discovery**: while the app hosts a lobby, `Bridge.startBeacon` sends a `lan.Beacon` every 2 s to the directed broadcast address of each IPv4 network on an up, broadcast-capable, non-loopback interface (a LAN, Radmin VPN's `26.0.0.0/8`) on UDP 25565 (`WW_LAN_PORT`); it stops with the session (and at once on Leave). While Home is shown the page polls `Bridge.LanSessions` every second, which opens a shared (`SO_REUSEADDR`) listener on that port, closed 5 s after the last poll or when a session starts; heard hosts are kept for 6 s after their last beacon (`lan.Table`: one entry per host app run and what its beacons say (a copy of a host's instance that names another port or name is its own row), its own beacons skipped, at most 64 hosts, 8 addresses each and 4 hosts per source address, addresses ranked LAN, Radmin VPN, Tailscale, other, then first heard). Home lists them under Join as "Sessions on your network": the host's name (masked as text, as a peer's name is), players, phase, co-op, its network's label and its address masked (Show per row), and a Join button; a host on another network protocol is greyed with its version and can't be joined. `WW_LISTEN_HOST=127.0.0.1` (or `localhost`, `::1`) keeps discovery on the machine (listener bound there, beacons sent to 127.255.255.255 and 127.0.0.1) for local checks, and any other host name or IPv6 address turns it off rather than fall back to every network; `WW_LAN=off` turns it off. Whether broadcasts cross Radmin VPN's virtual LAN is not verified yet.
- **Logging.** `report.Multi` fans one session's lines out to several reporters: the controller's event publisher, optionally `Options.Log` (stdout for the CLI), and optionally the session's own `Options.SessionLog` reporter, opened as the session starts with its starting `State` and closed once it has ended (the TUI's log file, below).

#### Co-op through the controller

A `--coop` session's questions and console (docs/08-coop-design.md §5, §6.7; Appendix C items 64, 70, 162, 163, 164) go through two seams in package main:

- **Questions: `coopAsker`.** A co-op session asks its bind and scrub questions through a `coopAsker` (`question(ctx, rep, session.Question) bool`). A `session.Question` has the kind (bind or scrub), the player, a one-line title, the whole prompt as the CLI prints it, and a bind's preflight lines. Two askers exist:
  - `coopPrompter`, the CLI's: today's stdin prompter, unchanged (y/N, `--yes`, EOF or a closed input is no, the 50 ms settle, Appendix C item 64). Its reader also takes the console commands.
  - `outputAsker`, the TUI's and the app window's (App PR 9: a dialog per question, Escape is no, `SetAutoYes` answers open and later questions yes for the session): it logs the question as the CLI does, then calls `Output.Ask`, which opens the question in the controller (`EventQuestion`, `State.Questions`) and waits for `Controller.Answer(id, yes)`. The session ending is a no (`EventQuestionClosed`). stdin is never read.
  - The far-behind, needs-merge and no-backup advice is logged as before and also published as `EventAdvice` (`session.Advice`).
- **Console: `coopConsole.exec`.** The verbs (`/refresh`, `/warp`, `/coop off|on`, `/status`, `/help`) run in `coopConsole.exec`. A line typed on stdin reaches it through `do`, as before; `Controller.Command(session.Command)` and `Controller.CommandLine(line)` reach it through `engine.Engine` (the co-op side's `engine.CoopSide`: `CoopCommand`, `CoopLine`). `Command` returns the refusal that kept a command from every pipeline (none runs yet, no such player, which player?), which is also logged; `CommandLine` only logs it. `/status`'s text is `formatStatus`, which `Snapshot().CoopStatus` also carries for a UI.
- **Front ends.** `coopEnv.front` (a `coopFront`) says which asker a session uses, who hears its advice, and hands the session to the engine (`attach`) for the console commands. Its zero value is the CLI's.

**The CLI.** `host` and `join` run on a controller over `newCLIEngine()`: no `engine.LiveState`, `Options.Log` is `report.Stdout`, and the stdin prompter answers the questions. `engine.RunCLISession` waits for the session and exits 1 when it ended `Failed`. The output, prompts, flags and exit codes are those of the direct calls it replaced: `mods/coop/session/golden_test.go` compares every co-op prompt and console flow with transcripts recorded before the change (`mods/coop/session/testdata/coop-golden`), and `TestRunCLISession` compares the driver with the old `logSessionErr` (now `engine.LogSessionErr`) + `os.Exit(1)` path. `mp-local` (two Dolphins in one process) still runs its pipelines directly, with the same stdin prompter and console.

**The TUI.** It masks the IP addresses it draws as the window does (`internal/redact`): the dashboard header's Host IPs or joined address, the log and chat panels and the end reason, and on the connect screen the Host IP field (a dot per character, like a password) and its error. **Ctrl+R** shows or masks them on every screen (the help line says which); the TUI doesn't save it. The CLI's `host` and `join` print the address to share on purpose, unmasked. The connect screen has a **Co-op** row (left/right): for a host Off, New world (from the file you load) or Continue *world* (from `CoopWorlds`, as `coop-world list` shows them); for a joiner Off or On. With co-op on, a dashboard line starting with `/` is a console command, the status panel gets a co-op line per pipeline, and an open question replaces the log panel until it is answered with `y` or `n`. A `y` or `n` counts only once the question has been shown, and the keyboard quiet, for 600 ms, so a key typed for the chat never answers it (Appendix C item 164). The dashboard's open questions are `Snapshot().Questions`, re-read on each status tick: a subscription may drop question events like any other.

### App environment: settings, logs, Dolphin, patching

App PR 3 adds the pieces the desktop app's first-run setup and session screens need, without changing the CLI (`cli_golden_test.go` compares `patch` and `dolphin2` with transcripts recorded before the change in `testdata/cli-golden`; `dolphinenv_equiv_test.go` compares the moved path and argument code with the old code kept verbatim in the test).

- **`internal/config`: the app's saved settings**, `<os.UserConfigDir>/ww-multiplayer/config.json` (the root co-op already uses for `worlds/` and `backups/`). Schema-versioned JSON (`version: 1`): name, color, recent hosts (10), port, Dolphin exe and user dir, launch-on-start and cheats switches, patched and vanilla ISO, the last co-op choice, window size and `setupDone`.
  - `Load` is tolerant and never fails. A missing file is `Defaults()`. A file that doesn't parse, or one over 1 MiB, gives the defaults and one warning, and is kept as `config.json.bad` by the next save that succeeds (moved there just before the new file is renamed into place, so a failed save leaves it where it was; later saves leave `.bad` alone). A file that can't be opened or read gives the defaults and a warning only. Top-level keys match without case, as the nested ones do (`"Name"` is read as `name`, an exact key winning), and are saved once, under their own name. A top-level section that doesn't decode, or a value out of range (port, a color `playercolor.Parse` refuses, co-op mode), gives that section's default and a warning; the rest is read.
  - `Save` is atomic (a temp file in the same directory, synced, renamed over the old one). It keeps fields this build doesn't know, top-level and inside known sections, and never lowers a newer build's schema version. `FuzzParse` checks that parse → save → parse is stable.
  - `WithEnv` applies `DOLPHIN_EXE`, `ISO_PATH`, `USER_DIR_1` and `WW_COLOR` over the settings for the app's run, never into the file.
  - **The CLI does not read it** (owner decision 11): scripts and tests stay deterministic, env vars remain the CLI's knobs. `TestCLIReadsNoConfig` keeps package main from importing it.
- **`internal/applog`: per-session log files.** Each session the TUI or the GUI runs writes `<UserConfigDir>/ww-multiplayer/logs/<UTC time>-<role>.log` through `Options.SessionLog` (`session_log.go`): a header line (build, OS, role, name, address, co-op), then every line the CLI would print, each stamped `2006-01-02T15:04:05.000Z LEVEL`. `Open` keeps the newest 20 files; a file stops at 8 MiB with one line saying so. Lines are redacted first: the home directory becomes `~` (it usually holds the account name) and values labelled `token`, `secret`, `password` or `api key` become `<redacted>` (the lobby's reconnect token is the first such value). The CLI's `host` and `join` write no file: their lines are on the terminal. `Diagnostics.Text` is the "Copy diagnostics" text (app version, OS, Dolphin path and version, user dir, log file, co-op `/status` lines, the last 200 log lines from `File.Tail`), redacted the same way. Nothing is uploaded.
- **`internal/dolphinenv` (`wwapi/emu/launch` since Phase C C10): Dolphin detection, user dirs, launch, cheats, the macOS prepare step.** The code `dolphin2` and `auto-recapture` used from `mp_local.go` moved here unchanged (`mp-local` used none of it and is untouched): `Defaults`/`DefaultPaths` (the per-OS fallbacks), `Paths.WithEnv`/`FromEnv` (`DOLPHIN_EXE`, `ISO_PATH`, `USER_DIR_1/2`), `Launch` (`-u <userDir> -e <iso> [--save_state=…]`, detached; `open -n -a` through LaunchServices on macOS, in `launch_darwin.go`), `BootstrapUserDir` (copy user dir 1 to 2 without `Cache/`), `EnsureCheatsIni` (main still embeds `cheats/GZLE01.ini` and passes it in). New for the app:
  - `Detect(Env)` tries, in order: a running Dolphin's own executable (Win32 `QueryFullProcessImageNameW`, macOS `ps -o comm=`), `DOLPHIN_EXE`, then on Windows `%ProgramFiles%\Dolphin`, `%ProgramFiles%\Dolphin-x64`, the installer's uninstall-registry `InstallLocation`, `%USERPROFILE%\Desktop\Dolphin-x64` (today's default) and scoop; on macOS `~/Applications/Dolphin.app` (the prepared copy) then `/Applications/Dolphin.app`; elsewhere `dolphin-emu` on `PATH`. It returns the first found and every candidate (with where it came from), or the default path to show beside "Browse…". `UserDir` gives `<exe dir>/User` when `portable.txt` sits beside the exe, else Dolphin's default (`DefaultUserDirs`, the same as `backup.DefaultUserDirs`).
  - `PrepareMac` runs `scripts/setup-mac-dolphin.sh`'s steps as Go through a `Runner` (copy to `~/Applications`, strip xattrs, `CFBundleIdentifier` `org.dolphin-emu.dolphin-unhardened`, ad-hoc `codesign` without the hardened runtime, `lsregister -f`, verify), logging the script's lines; no step needs sudo. The steps are `MacPlan(src, dst)`, a pure list a test checks against the script without running anything, and `MacVerify`; `PrepareMacHere` and `MacStatusHere` (this Mac) are in the darwin-only `macprep_darwin.go`. `MacCheck` says whether it is needed: no copy, a copy that still has the hardened runtime, or a copy whose `Info.plist` version differs from the original's ("Dolphin was updated — refresh the copy"). The script stays for CLI users.
  - Everything that decides is a pure function of an `Env` (or its arguments) and is tested with fakes on any OS; only `detect_windows.go`, `detect_darwin.go`, `detect_other.go`, `launch_darwin.go` and `launch_other.go` ask the OS. No test starts Dolphin.
- **`internal/patch`: `patch` as a function.** `patch.Run(ctx, in, out, w, Options) (Result, error)` writes the patcher's lines on `w` and returns errors instead of exiting: an input that already holds this build's mod is `Result.AlreadyPatched` (not an error), one patched by another build wraps `inject.ErrPatchedByOtherVersion`, the rest are `inject.PatchISO`'s errors, each also written as the CLI prints it. `Options.PostPatch` are the loaded mods' post-patch steps (`wwapi.PostPatcher`, main's `postPatchSteps`: co-op's `stagetables.CacheForPatch`), run in order, never failing the patch. `DefaultOut` is the `<input>-multiplayer.iso` rule. `Inspect(path)` says whether a disc is vanilla, patched by this build or by another, from its header, FST and `main.dol` alone. `runPatch` is now `patch.Run` on stdout plus `os.Exit(1)` on an error, with the output and exit codes it always had.
