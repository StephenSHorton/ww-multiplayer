# Architecture

## Goal

Enable two players to see each other in Wind Waker on Dolphin — each player runs their own Dolphin instance with their own save, and sees the other player's Link walking around in real-time.

## Three-Layer Design

```
┌──────────────────────────────────────────────────────────┐
│                    Player A's Machine                    │
│                                                          │
│  ┌─────────────┐     ┌──────────────┐     ┌──────────┐  │
│  │   Dolphin   │◄───►│  ww-mult Go  │◄───►│  Server  │  │
│  │ + WW (GZLE01)│    │              │     │(TCP:25565)│  │
│  └─────────────┘     └──────────────┘     └────┬─────┘  │
│         ▲                    │                 │        │
│         │                    │                 │        │
│         └─ ReadProcessMemory │                 │        │
│         └─ WriteProcessMemory│                 │        │
│                                                │        │
│                                                │        │
└────────────────────────────────────────────────┼────────┘
                                                 │
                                          TCP over LAN
                                                 │
┌────────────────────────────────────────────────┼────────┐
│                    Player B's Machine          │        │
│                                                 │        │
│  ┌─────────────┐     ┌──────────────┐         │        │
│  │   Dolphin   │◄───►│  ww-mult Go  │◄────────┘        │
│  │ + WW (GZLE01)│    │ (client mode)│                  │
│  └─────────────┘     └──────────────┘                  │
└──────────────────────────────────────────────────────────┘
```

## Data Flow

1. Each Go client reads its local player's position from Dolphin memory at ~60fps (50ms intervals).
2. Position data is sent to the server via TCP.
3. Server broadcasts position to all other clients.
4. Each client writes the received position to a "second Link" actor in its Dolphin memory.
5. The game renders the second actor at the received position, creating the illusion of another player.

## Components

### `internal/dolphin/`

Windows process memory access via `kernel32.dll` P/Invoke (ReadProcessMemory / WriteProcessMemory). Handles:
- Process discovery (find Dolphin.exe)
- Memory base scanning (locate emulated GameCube RAM in Dolphin's process — works on any Dolphin version including modern 64-bit builds)
- Big-endian / little-endian conversion (GameCube is big-endian, x86 is little-endian)
- Read/write at absolute GC addresses

### `internal/network/`

Simple TCP-based protocol with message framing (`[type:1][length:2][data]`). Message types:
- `J` (Join) — client announces name
- `H` (Hello) — protocol version, and from protocol 2 the connection role and caps (`handshake.go`)
- `W` (Welcome) — server assigns an ID; `R` (Reject) — the server refuses the connection, with a code and a reason
- `P` (Position) — 18-byte position update (3 floats + 3 int16s); `M` (Pose) — the skeletal pose
- `L` (PlayerList) — server announces who's connected (with the tunic-color trailer, docs/09); `D` (Leave)
- `C` (Chat) — text messages
- `K` / `Q` (Ping / Pong) — heartbeat and RTT
- `O` (Coop) — co-op sub-messages, on a co-op connection only (docs/08)
- `B` (Lobby) — lobby sub-messages with JSON bodies, on a lobby connection only (docs/10-lobby.md)

A connection has one of three roles, set in its hello: a **player** (pose, position, chat and the roster; every CLI connection), a **co-op** connection (`RoleCoop`, the co-op pipeline), or a **lobby** connection (`RoleLobby`, the desktop app's pre-game lobby: members, colors, ready flags, the host's co-op settings, Start). Co-op and lobby connections are never players: not in the roster, the player count or the relays. Every server has a lobby (`LobbyHub`), inert until a lobby connection arrives; a server from before the lobby refuses the role with `RejectRole`, and the app then joins directly, so the protocol version stayed 2. The server's `CoopHandler` can be set after `Start` (`Server.SetCoop`); while the lobby's host has chosen co-op and the session isn't in game yet, a co-op hello is held for it instead of refused, and `Stop` releases a held one (docs/10-lobby.md §7). A name the lobby's host kicked gets `MsgReject` (`RejectBadName`) on player and co-op connections until the lobby empties, so a reconnecting CLI join stops. Lobby connections are rate-limited and STATE is merged per connection, so a member can't make the server flood the others (docs/10-lobby.md §3).

Server runs on port `25565`. UDP would be lower-latency for position data but TCP is fine for LAN play.

### Front ends and `internal/session`

One exe has three faces (`app_face.go`). Every subcommand is the CLI, dispatched by main's switch exactly as before; running with no arguments opens the desktop app window (`internal/gui`, below), or, in a build without the window, the Bubble Tea TUI (`internal/tui`, brought back in v0.1.5 after v0.1.2 removed the v0.0 one), which `ww-multiplayer tui` always opens; `ui` opens the window too and `ui --browser` serves its UI to a browser. `TestCLISubcommandsUnchanged` pins main's subcommand list to the one before the window (`testdata/cli-subcommands.txt`) and checks none of them opens anything but the CLI. The CLI faces:

- `ww-multiplayer.exe host` / `ww-multiplayer.exe join <ip>` — the user-facing multiplayer entry points (one process per player; signal handler resets the mailbox on Ctrl+C).
- `ww-multiplayer.exe server` / `broadcast-pose` / `puppet-sync` — lower-level building blocks used by `scripts/mplay2.sh` for two-Dolphin local harness.
- `ww-multiplayer.exe debug`, `ww-multiplayer.exe dump`, `ww-multiplayer.exe shadow-mode` — diagnostic CLIs. Plain-text output — good for piping into agents.

The front ends do not call the session code directly. They drive a **session controller** (`internal/session`), the UI-free owner of a session's state that the planned desktop app will drive too:

```
CLI host / join        TUI (internal/tui)        GUI (internal/gui + frontend)
        │ commands: Host, Join, Leave, SendChat; co-op: Answer, Command, CommandLine
        │ lobby: HostLobby, JoinLobby, SetColor, SetReady, SetCoopSettings, Start, Go, Kick, RequestMerge
        │ out: Snapshot() State, Subscribe() <-chan Event, Wait(id) State
session.Controller (internal/session)
        │ Engine (+ CoopEngine) interface, injected by main
sessionEngine (session_engine.go) ── runHostSession / runJoinSession (+ liveState for the TUI and GUI)
```

- **Commands in.** `Host(ctx, HostOptions)` and `Join(ctx, JoinOptions)` start a session in the background and return its `ID` (one session at a time; `ErrBusy` otherwise). The options carry the port (host) and the co-op choices (`CoopOptions`, the `--coop` flags). `Leave` cancels it and returns once teardown is done (pipelines stopped, server unbound, mailbox reset), so the next Host can bind the port. `SendChat` forwards a line to the running session. `Wait(id)` blocks until a session has ended and returns its final state.
- **State out.** `Snapshot()` returns a copy of the current session's `State`: ID, phase (`Idle → InGame → Ended`), role, name, address, end reason, `Failed` (it ended on an error), its co-op options, its open co-op questions, and the live values (players, player count, host addresses, latency, own position, each co-op pipeline's `CoopStatus`) the engine reads from `liveState` and the co-op console. The dashboard polls it every 250 ms.
- **Events out.** `Subscribe()` gives each UI its own buffered channel of `Event`s: `EventLog` (every `report.Reporter` line), `EventChat`, `EventEnded` (with the end reason: the newest Err-level line, or "no error was reported"), `EventState`, and for co-op `EventQuestion`, `EventQuestionClosed` and `EventAdvice`. Every event carries the session `ID`, so a UI ignores late events from a session it has left. A full buffer drops its *oldest* event, so a slow UI never stalls broadcast-pose or puppet-sync and a session's last two events (`EventEnded`, then `EventState`) always get in (`New` keeps every buffer at 2 slots or more for that).
- **Engine.** `internal/session` imports neither `internal/dolphin` nor `internal/network`; package main injects the work as a `session.Engine`. `sessionEngine` runs `runHostSession` / `runJoinSession`, hands them a per-session `session.Output` (a `report.Reporter`, a chat sink, `Ask` and `Advise`) and reads `liveState` for `Live()`. An engine that also implements `session.CoopEngine` (`Command`, `CommandLine`, `CoopWorlds`) takes the co-op console verbs; the controller finds it by a type assertion, so an engine without co-op needn't. An engine error that the session already logged (a fatal connect error) wraps `ErrReported`: the controller doesn't log it again but still marks the session `Failed`. The controller is unit-tested on any OS with a fake engine.
- **The lobby.** `HostLobby` and `JoinLobby` start a session that begins in the pre-game lobby (docs/10-lobby.md). Its phase follows the host's lobby, `Connecting → InLobby → Starting → InGame` (the new phases are numbered after `Ended`, so the old values keep theirs), and `State.Lobby` holds the lobby's view: this player's member ID and host flag, the phase, the co-op settings and every member (name, color, ready, Dolphin state, file hint, RTT, `app` or `cli`, away). The lobby commands (`SetColor`, `SetReady`, `SetDolphin`, `SetFile`, and for the host `SetCoopSettings`, `Start`, `Go`, `Kick`; `RequestMerge`) go to an engine that also implements `session.LobbyEngine`, found by a type assertion like `CoopEngine`; the controller refuses what the role or phase rules out (`ErrNotHost`, `ErrWrongPhase`, `ErrColorsLocked`, `ErrNoLobby`) before anything is sent. The host's replies arrive as `EventLobbyNotice`, `EventLobbyStart`, `EventLobbyGo` and `EventLobbyRequest`. A host whose build has no lobby makes `JoinLobby` fall back to the direct `Join` in the same session (`EventLegacyHost`, `State.Lobby.Legacy`), which the GUI does automatically (owner decision), keeping the chosen color (`JoinOptions.Color` reaches the direct join's player connections). A member that joins or reconnects after Start still gets `EventLobbyStart` (and, in game, `EventLobbyGo` with the world); handlers treat a repeat as idempotent. `sessionEngine`'s lobby side is `lobby_engine.go`; what Start launches comes in a later PR, and no CLI subcommand opens a lobby.
- **The app window (`internal/gui`, App PR 5).** A Wails v2 window (WebView2 on Windows, WKWebView on macOS) over a plain HTML/CSS/ES-module frontend (`internal/gui/frontend`, embedded, no build step; styled after the game's pause menu, owner decision 2026-10-16, drawn in CSS with no game assets, with the site's fonts vendored under the SIL OFL). Its Home screen takes a name and a tunic color (the `playercolor` palette, green first, or a custom `#RRGGBB`; none chosen = classic green) and hosts or joins through `HostLobby` / `JoinLobby`; its Session screen lists the lobby's members with their colors and ready flags (your own color and ready toggle while in the lobby phase), or a direct session's players, with the session log and chat; Leave and closing the window (which asks first while a session runs) end the session through `Leave`. The forms start from and save the app's config (name, color, port, recent hosts; env overrides apply, `internal/config`); package main never imports `internal/config`, so the CLI still can't read it. Everything the frontend does goes through `Bridge` (`bridge.go`), whose exported methods (`Info`, `State`, `Host`, `Join`, `Leave`, `SetColor`, `SetReady`, `SendChat`, and the setup's, below) are the whole JS API, and one JS module, `transport.js`: in the window it calls Wails' binding of `Bridge` and listens for the `ww:event` event; under `ui --browser` (`browser.go`, pure Go, every OS) it posts the same calls to `/api/call/<Method>` and reads the controller's events as server-sent events from `/api/events`. That server binds `127.0.0.1` only and checks a per-run token, the `Host` header and any `Origin`, so web pages and DNS rebinding can't reach it, and it serves only the methods `browserMethods` names (every one but the window-only `PickFile`).
  - **First-run setup (App PR 6, `setup.go`, `setup_patch.go`, `frontend/setup.js`).** The window opens on Setup while the effective config (env overrides applied) has no name, no patched disc or no Dolphin, or a saved disc or Dolphin is no longer a file (`setupGaps`), or on macOS the prepared copy of Dolphin is missing or still hardened, or the saved Dolphin is the original `/Applications` one (`macGap`); Home's Setup button reopens it, and each step can be skipped. (1) Name and tunic color: the palette (classic green when none is chosen) or a custom `#RRGGBB` (`CheckColor`), with our own flat SVG Link whose tunic takes the color (no game art); `SaveProfile`. Players may share a color, so nothing warns about close colors (owner decision 2026-10-16). (2) The game: `PickFile("iso")` (Wails' native dialog; in `ui --browser` a typed path instead) then `StartPatch`, which runs `patch.Run` in a goroutine with main's `cacheCoopTablesForPatch` as `CoopTables`. The patcher's own lines (unchanged CLI text) become a `PatchView` (`applyPatchLine`: stage, percent, the "Co-op tables built" row or the patcher's warning, already patched, error), sent as `patch` events and read with `PatchStatus`; the bar creeps while `inject.PatchISO` runs, since that step says nothing until done. "I already have a patched ISO" checks the disc first with `patch.Inspect` (header, FST and `main.dol` only) and refuses a vanilla disc or another build's. On success the config gets `iso.patched` (and `iso.vanilla` when it patched now). `CancelPatch` stops a patch before it reads the disc, and skips the co-op tables step once cancelled; after that `PatchISO` can't be interrupted, so the cancelled patch finishes writing and its new output is removed, except when it was written over an earlier `<name>-multiplayer.iso`: that one is already replaced, so the new, complete disc is kept, and the view says which happened (`PatchView.stopped`). Each `PatchView` carries a `seq` so the frontend drops a snapshot older than the one it shows. Closing the window during a patch asks first (`Bridge.beforeClose`, which asks every question before acting, so "Stay" changes nothing); on "Close" it cancels the patch and keeps the window open, showing "Stopping…", until the patch has ended, then quits. `Bridge.close` (window shutdown, `ui --browser` Ctrl+C) also waits for the patch with no time limit; `PatchISO` writes a temp file and renames it, so nothing half-written is left. (3) Dolphin: `DetectDolphin` (`dolphinenv.Detect` and `UserDir`), Browse… (`PickFile("dolphin")`, a `.app` taken as its program, a folder as the Dolphin in it), the user folder, `SetDolphin`. Until the player types or browses a user folder, the box follows the chosen Dolphin (`UserDirFor`: its `User` folder when portable, else Dolphin's default). On macOS `MacStatusHere` (`GatherMacFacts`, which reads both bundles' versions with `plutil -extract` so binary plists work too, + `MacCheck`, in `macprep_darwin.go`) adds the Prepare Dolphin card (#16), and an outdated copy also gets a "Dolphin was updated — refresh the copy" toast at launch; `PrepareDolphin` runs `PrepareMacHere`, whose steps are the pure `MacPlan` (copy, strip xattrs, `CFBundleIdentifier`, ad-hoc `codesign` without the hardened runtime, `lsregister -f`) then `MacVerify`, and saves the prepared copy when no other Dolphin was chosen; it refuses while Dolphin runs from the copy ("Close Dolphin first"), since it starts by removing the old copy. (4) "You're set": `FinishSetup` sets `ui.setupDone`. Nothing here launches Dolphin, and the CLI is unchanged (`patch` still prints and exits as before).
  - **Build tags.** The Wails file (`app_wails.go`) builds only for `(windows || darwin) && desktop && production`; every other build (plain `go build`, Linux) gets `gui_nogui.go`, whose `Run` returns `ErrNoGUI` and `Available()` false, so it never imports Wails and no-args opens the TUI as before. Wails v2 itself won't start a window without `production`, which is why the tag gate is ours. The release and CI builds pass `-tags desktop,production` (`TestGUIBuildTags` checks they do); Windows needs no cgo for it (go-webview2 is syscalls), so the Linux cross-build keeps `CGO_ENABLED=0`, and the native Linux CI job never compiles Wails (no GTK/webkit).
  - **Windows console.** The exe stays a console-subsystem program, so the CLI prints and reads stdin as before. Double-clicked, it owns its console (`GetConsoleProcessList` returns 1): the window hides that console while it starts and frees it once the window is up; if the window fails first (no WebView2 and the user declined Wails' installer prompt) the console comes back and the TUI opens in it with a line saying why. Started from a terminal, the console is shared and left alone.
- **Logging.** `report.Multi` fans one session's lines out to several reporters: the controller's event publisher, optionally `Options.Log` (stdout for the CLI), and optionally the session's own `Options.SessionLog` reporter, opened as the session starts with its starting `State` and closed once it has ended (the TUI's log file, below).

#### Co-op through the controller

A `--coop` session's questions and console (docs/08-coop-design.md §5, §6.7; Appendix C items 64, 70, 162, 163, 164) go through two seams in package main:

- **Questions: `coopAsker`.** A co-op session asks its bind and scrub questions through a `coopAsker` (`question(ctx, rep, session.Question) bool`). A `session.Question` has the kind (bind or scrub), the player, a one-line title, the whole prompt as the CLI prints it, and a bind's preflight lines. Two askers exist:
  - `coopPrompter`, the CLI's: today's stdin prompter, unchanged (y/N, `--yes`, EOF or a closed input is no, the 50 ms settle, Appendix C item 64). Its reader also takes the console commands.
  - `outputAsker`, the TUI's (and the GUI's later): it logs the question as the CLI does, then calls `Output.Ask`, which opens the question in the controller (`EventQuestion`, `State.Questions`) and waits for `Controller.Answer(id, yes)`. The session ending is a no (`EventQuestionClosed`). stdin is never read.
  - The far-behind, needs-merge and no-backup advice is logged as before and also published as `EventAdvice` (`session.Advice`).
- **Console: `coopConsole.exec`.** The verbs (`/refresh`, `/warp`, `/coop off|on`, `/status`, `/help`) run in `coopConsole.exec`. A line typed on stdin reaches it through `do`, as before; `Controller.Command(session.Command)` and `Controller.CommandLine(line)` reach it through `sessionEngine`. `Command` returns the refusal that kept a command from every pipeline (none runs yet, no such player, which player?), which is also logged; `CommandLine` only logs it. `/status`'s text is `formatStatus`, which `Snapshot().CoopStatus` also carries for a UI.
- **Front ends.** `coopEnv.front` (a `coopFront`) says which asker a session uses, who hears its advice, and hands the session to the engine (`attach`) for the console commands. Its zero value is the CLI's.

**The CLI.** `host` and `join` run on a controller over `newCLIEngine()`: no `liveState`, `Options.Log` is `report.Stdout`, and the stdin prompter answers the questions. `runCLISession` waits for the session and exits 1 when it ended `Failed`. The output, prompts, flags and exit codes are those of the direct calls it replaced: `coop_golden_test.go` compares every co-op prompt and console flow with transcripts recorded before the change (`testdata/coop-golden`), and `TestRunCLISession` compares the driver with the old `logSessionErr` + `os.Exit(1)` path. `mp-local` (two Dolphins in one process) still runs its pipelines directly, with the same stdin prompter and console.

**The TUI.** The connect screen has a **Co-op** row (left/right): for a host Off, New world (from the file you load) or Continue *world* (from `CoopWorlds`, as `coop-world list` shows them); for a joiner Off or On. With co-op on, a dashboard line starting with `/` is a console command, the status panel gets a co-op line per pipeline, and an open question replaces the log panel until it is answered with `y` or `n`. A `y` or `n` counts only once the question has been shown, and the keyboard quiet, for 600 ms, so a key typed for the chat never answers it (Appendix C item 164). The dashboard's open questions are `Snapshot().Questions`, re-read on each status tick: a subscription may drop question events like any other.

### App environment: settings, logs, Dolphin, patching

App PR 3 adds the pieces the desktop app's first-run setup and session screens need, without changing the CLI (`cli_golden_test.go` compares `patch` and `dolphin2` with transcripts recorded before the change in `testdata/cli-golden`; `dolphinenv_equiv_test.go` compares the moved path and argument code with the old code kept verbatim in the test).

- **`internal/config`: the app's saved settings**, `<os.UserConfigDir>/ww-multiplayer/config.json` (the root co-op already uses for `worlds/` and `backups/`). Schema-versioned JSON (`version: 1`): name, color, recent hosts (10), port, Dolphin exe and user dir, launch-on-start and cheats switches, patched and vanilla ISO, the last co-op choice, window size and `setupDone`.
  - `Load` is tolerant and never fails. A missing file is `Defaults()`. A file that doesn't parse, or one over 1 MiB, gives the defaults and one warning, and is kept as `config.json.bad` by the next save that succeeds (moved there just before the new file is renamed into place, so a failed save leaves it where it was; later saves leave `.bad` alone). A file that can't be opened or read gives the defaults and a warning only. Top-level keys match without case, as the nested ones do (`"Name"` is read as `name`, an exact key winning), and are saved once, under their own name. A top-level section that doesn't decode, or a value out of range (port, a color `playercolor.Parse` refuses, co-op mode), gives that section's default and a warning; the rest is read.
  - `Save` is atomic (a temp file in the same directory, synced, renamed over the old one). It keeps fields this build doesn't know, top-level and inside known sections, and never lowers a newer build's schema version. `FuzzParse` checks that parse → save → parse is stable.
  - `WithEnv` applies `DOLPHIN_EXE`, `ISO_PATH`, `USER_DIR_1` and `WW_COLOR` over the settings for the app's run, never into the file.
  - **The CLI does not read it** (owner decision 11): scripts and tests stay deterministic, env vars remain the CLI's knobs. `TestCLIReadsNoConfig` keeps package main from importing it.
- **`internal/applog`: per-session log files.** Each session the TUI or the GUI runs writes `<UserConfigDir>/ww-multiplayer/logs/<UTC time>-<role>.log` through `Options.SessionLog` (`session_log.go`): a header line (build, OS, role, name, address, co-op), then every line the CLI would print, each stamped `2006-01-02T15:04:05.000Z LEVEL`. `Open` keeps the newest 20 files; a file stops at 8 MiB with one line saying so. Lines are redacted first: the home directory becomes `~` (it usually holds the account name) and values labelled `token`, `secret`, `password` or `api key` become `<redacted>` (the lobby's reconnect token is the first such value). The CLI's `host` and `join` write no file: their lines are on the terminal. `Diagnostics.Text` is the "Copy diagnostics" text (app version, OS, Dolphin path and version, user dir, log file, co-op `/status` lines, the last 200 log lines from `File.Tail`), redacted the same way. Nothing is uploaded.
- **`internal/dolphinenv`: Dolphin detection, user dirs, launch, cheats, the macOS prepare step.** The code `dolphin2` and `auto-recapture` used from `mp_local.go` moved here unchanged (`mp-local` used none of it and is untouched): `Defaults`/`DefaultPaths` (the per-OS fallbacks), `Paths.WithEnv`/`FromEnv` (`DOLPHIN_EXE`, `ISO_PATH`, `USER_DIR_1/2`), `Launch` (`-u <userDir> -e <iso> [--save_state=…]`, detached; `open -n -a` through LaunchServices on macOS, in `launch_darwin.go`), `BootstrapUserDir` (copy user dir 1 to 2 without `Cache/`), `EnsureCheatsIni` (main still embeds `cheats/GZLE01.ini` and passes it in). New for the app:
  - `Detect(Env)` tries, in order: a running Dolphin's own executable (Win32 `QueryFullProcessImageNameW`, macOS `ps -o comm=`), `DOLPHIN_EXE`, then on Windows `%ProgramFiles%\Dolphin`, `%ProgramFiles%\Dolphin-x64`, the installer's uninstall-registry `InstallLocation`, `%USERPROFILE%\Desktop\Dolphin-x64` (today's default) and scoop; on macOS `~/Applications/Dolphin.app` (the prepared copy) then `/Applications/Dolphin.app`; elsewhere `dolphin-emu` on `PATH`. It returns the first found and every candidate (with where it came from), or the default path to show beside "Browse…". `UserDir` gives `<exe dir>/User` when `portable.txt` sits beside the exe, else Dolphin's default (`DefaultUserDirs`, the same as `backup.DefaultUserDirs`).
  - `PrepareMac` runs `scripts/setup-mac-dolphin.sh`'s steps as Go through a `Runner` (copy to `~/Applications`, strip xattrs, `CFBundleIdentifier` `org.dolphin-emu.dolphin-unhardened`, ad-hoc `codesign` without the hardened runtime, `lsregister -f`, verify), logging the script's lines; no step needs sudo. The steps are `MacPlan(src, dst)`, a pure list a test checks against the script without running anything, and `MacVerify`; `PrepareMacHere` and `MacStatusHere` (this Mac) are in the darwin-only `macprep_darwin.go`. `MacCheck` says whether it is needed: no copy, a copy that still has the hardened runtime, or a copy whose `Info.plist` version differs from the original's ("Dolphin was updated — refresh the copy"). The script stays for CLI users.
  - Everything that decides is a pure function of an `Env` (or its arguments) and is tested with fakes on any OS; only `detect_windows.go`, `detect_darwin.go`, `detect_other.go`, `launch_darwin.go` and `launch_other.go` ask the OS. No test starts Dolphin.
- **`internal/patch`: `patch` as a function.** `patch.Run(ctx, in, out, w, Options) (Result, error)` writes the patcher's lines on `w` and returns errors instead of exiting: an input that already holds this build's mod is `Result.AlreadyPatched` (not an error), one patched by another build wraps `inject.ErrPatchedByOtherVersion`, the rest are `inject.PatchISO`'s errors, each also written as the CLI prints it. `Options.CoopTables` is main's `cacheCoopTablesForPatch`. `DefaultOut` is the `<input>-multiplayer.iso` rule. `Inspect(path)` says whether a disc is vanilla, patched by this build or by another, from its header, FST and `main.dol` alone. `runPatch` is now `patch.Run` on stdout plus `os.Exit(1)` on an error, with the output and exit codes it always had.
